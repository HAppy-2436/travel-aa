## 一、总体架构：一份内核，三端复用

```
                    ┌──────────────────────────────┐
                    │  apps/miniprogram/utils/     │
                    │   ai.js     ← 解析/分类/审计 │
                    │   ctrip.js  ← 携程订单解析   │
                    │   settle.js ← 结算算法       │
                    │   （UMD 模块）               │
                    └───────────┬──────────────────┘
        ┌───────────────────────┼───────────────────────┐
        ▼                       ▼                       ▼
  网页 Demo               微信小程序                Node 服务端
 demo/index.html      apps/miniprogram/          server/app.js
 <script src=...>      require('../../utils/')    require('../apps/...')
```

**为什么这样做**：AA 记账的正确性集中在算法（分摊尾差、汇率折算、最简转账）。
三端各写一份必然漂移，所以**只维护一处**，三端引用同一份文件。

> ⚠️ 改算法只改 `ai.js` / `ctrip.js` / `settle.js`；**不要**在 Demo 或 server 里复制业务逻辑。

## 二、数据模型

### 房间 Room

```js
{
  id: 'room_1',
  name: '国庆东京行',
  destination: '东京',
  code: '888666',            // 6 位房间号，全局唯一
  creator: 'u1',
  members: [{ id: 'u1', name: '小明' }, ...],
  budgetPerPerson: 5000,     // 人均预算（0 = 未设置）
  startDate: '2024-10-01',   // 用于预算燃烧率/报告
  endDate: '2024-10-05'
}
```

### 账单 Bill（统一由 `makeBill()` 构造，字段不可缺）

```js
{
  id: 'bill_7', roomId: 'room_1',
  payer: 'u1', payerName: '小明',
  amount: 12000,             // 原币金额
  currency: 'JPY',           // 币种（默认 CNY）
  rate: 0.048,               // 记账时汇率快照
  cnyAmount: 576,            // 折算后人民币（结算与统计都用它）
  description: '京都一日游交通',
  category: 'transport',     // food/transport/hotel/ticket/shopping/other
  splits: [{ memberId:'u1', memberName:'小明', amount: 192 }, ...],  // 分摊明细
  source: 'ai',              // manual / ai / ocr / ctrip（入账来源，统计页会汇总）
  timeStr: '2024-10-04',     // 展示用
  createdAt: '2024-10-04T09:00:00.000Z'  // 统计按天聚合依赖它
}
```

**约定**：
- `splits` 的金额之和 **必须等于 `amount`（原币口径）**，不是 `cnyAmount`。
  外币账单的分摊仍是日元/美元原值，折算只发生在 `cnyAmount` 与结算的 `netBalances` 里。
  ⚠️ 照"等于 cnyAmount"去构造 splits 会把外币账单直接 400 拒掉（server 按分位严格比较 `Σsplits === amount`）。
- 记账时用 `allocateEvenly()` 生成均分，避免 `100/3` 这类尾差；抹零走 `applyRoundingLoss()`，
  把差额并成一笔独立的「抹零损耗」行，合计仍严格等于 `amount`；
- 外币账单结算时按 `bill.rate`（快照汇率）折算成人民币再加总，保证**账恒平**（净余额合计严格为 0）；
- 调整单（`isAdjustment: true`）是**零和重分配**或**总额变更**：`Σadj = delta`，
  其中"排除某人 / 多退少补"是零和，"暂估改价 / 补记"会改总额；
- `createdAt` 缺失的历史数据不会出现在「每日消费」里。

**字段补充**：`scope`（`group` / `personal`，私账=人情账，不计入房间总消费）、
`splitType`（`equal` / `treat` / `sole`）、`roundedLoss`、`status`（`draft` = 占位账单，结算前需补齐）、
`updatedAt`（同步层 LWW 判新旧用，由 Demo 在发布前按内容 diff 盖上）。

## 四、算法口径（正确性关键）

| 算法 | 位置 | 口径 |
|---|---|---|
| 均分尾差安全 | `ai.js#allocateEvenly` | 最大余额法：`100/3 → [33.34, 33.33, 33.33]`，合计恒等 |
| 多币种折算 | `ai.js#toCNY` / `#billCNY` | 记账时快照 `rate`，优先用 `cnyAmount`，回退实时汇率 |
| 最简转账 | `demo/index.html#calcSettlement`、`settle.js` | 贪心：最大债务人与最大债权人两两配对，直到平账 |
| 账恒平 | 结算聚合 | 每人净余额合计 = 0（自检项之一）；外币分摊按比例缩放 |
| 账单审计 | `ai.js#auditBills` | 重复记账、账不平、异常大额、漏归类 → 问题列表 + 健康度评分 |
| 预算状态 | `ai.js#budgetStatus` | 燃烧率、按当前速度的支出预测、是否将超支、剩余日均可用额 |
| 每日统计 | `ai.js#dailyStats` | 按 `createdAt` 聚合每日总额、最贵一天、趋势（up/down/flat） |
| 消费洞察 | `ai.js#generateInsight` | 人均/日均/消费大头/最大单笔 + 建议列表 |
| 旅行小作文 | `ai.js#generateNarrative` | 模板保底（离线），可选 LLM 润色 |

## 五、Demo 渲染架构（`demo/index.html`）

```
State = { rooms[], bills[], tombstones{}, nextRoomId, nextBillId, phoneCount }   ← 唯一数据源
USERS = [ {id, name, color, role, _page, _roomId, _form, _aiText, _narr, ...} ]

renderPhones()  → 渲染 N 个手机外壳（含 toast / 确认弹窗容器）
renderApp(u)    → 按 u._page 渲染该手机的整个 App：
                  home / room / add / capture / settle / stats
syncAll()       → 所有可见手机重渲染 + 高亮闪烁动画 + publishSoon() 广播/落盘
```

- **页面状态挂在 user 对象上**（`_page`/`_roomId`/`_form`…），所以每台手机相互独立，又共享同一份 `State`。
- 表单输入用 `oninput` 只写状态**不重渲染**（避免输入框失焦）；切换类操作才 `renderApp`。
- 新增页面只需三步：`renderXxx()` 函数 → `renderApp` 里加路由分支 → `titles` 加标题。
- 演示保障：`TOUR_STEPS`（15 步导览，含 `before()` 状态准备）、`runSelfTest()`（22 项功能自检）、`runUITest()`（交互验收，含无障碍）、`runTourTest()`（导览目标校验）。
- **导航模型**（不要改坏）：每个页面都遵循「左侧 `←` 返回上一级 · 标题点按回首页 · 右侧 `STATS`（仅首页/房间页）」；
  `phoneGoBack()` 保证 `add/capture/settle/stats → room → home` 的链路永不断裂，房间失效时直接回首页（`emBack()` 提供显式出口）。

### 五-②、同步层：从「单页模拟」到「真多窗口 + 刷新不丢」

改造前「4 台手机实时同步」是**单页模拟**——共享同一份内存 `State`，刷新即全丢，也无法开两个窗口协同。
现在接上共享内核 `apps/miniprogram/utils/sync.js`（同一份 UMD，零依赖、零服务器）：

| 通道 | 能力 | 降级顺序 |
|---|---|---|
| `BroadcastChannel` | 同浏览器多窗口**秒级**同步 | 构造失败 → |
| `localStorage` + `storage` 事件 | 同浏览器多窗口同步 + **刷新不丢** | 探测失败 → |
| 内存 | 单页模拟，行为与改造前逐字节等价 | — |

**探测是运行时的**，不是按协议写死的：`hasLocalStorage()` 真的 `setItem` 一次并删掉，抛异常才判定不可用。
实测（`docs/效果截图` 里曾放过的探针页，Edge headless + `file://`）：`localStorage` 可写、**跨浏览器进程重启仍读到上一轮写入**，
`new BroadcastChannel()` 也能构造成功。所以 `file://` 双击打开同样刷新不丢。
⚠️ 但"能构造"不等于"消息真能跨窗口投递"，所以**徽标不拿构造结果当依据**：
开局在 `…presence` 频道发一次 hello，**收到对端 hello/ack 才显示 `🔗 多窗口已同步`**，否则显示 `💾 已开启本地留存`。

接线要点（**改这部分前先看这些坑**）：

- `syncAll()` 是唯一写出口，末尾调 `publishSoon()`（60ms 去抖），远端合并触发时不回环广播（`SyncApplyingRemote` 守卫）。
- **`rev` 必须全局单调**：原来是每窗口局部计数器、都从 0 开始 → 未收到对方快照就先写的一方会发出相同 `rev`，
  被 `stale-rev` 丢弃、**数据永久同步不过去**。现在取 `max(本地 rev, 共享存储里的 rev, 墙钟毫秒×1000) + 1`，
  且 `receive()` 只丢弃**更旧**的 rev（相等放行，交给按 `updatedAt` 的 LWW 合并兜底）。
- **发布前给"内容确实变了"的实体盖 `updatedAt`**（`stampChanged()`，用指纹 diff）：Demo 的房间/账单只有
  `createdAt`，加入成员这类**原地修改**不更新时间戳 → 合并时两边相等、本地旧副本胜出、对方的修改被静默丢掉。
  反之若全量盖章，本地会永远赢，同样错。合并回来时用 `applyRemote()` 重新记录指纹。
- **删除必须留墓碑**（`State.tombstones`）：否则对方窗口的旧快照一合并，被删的账单就"复活"了。
- 合并后 `reseedCounters()` 把 `nextBillId/nextRoomId` 抬到已有最大编号之上，避免两个窗口都生成 `bill_1`。
- 带演示/自检 hash（`#auto`/`#v3demo`/`#selftest`/`#uitest`/`?stage=`）时**不回填**旧数据，保证截图与自检可复现。

> 诚实边界：本模块解决的是**同一浏览器多窗口**的真实同步。跨设备/跨浏览器需要后端通道
> （`server/` 已具备 REST 接口），不在本模块范围内。

## 五+. 排版规范与无障碍（改样式前必读）

手机框宽 320px，字号分两档，**不要一刀切**：

| 档位 | 用途 | 字号 |
|---|---|---|
| **主视觉（允许大）** | 首屏 slogan（`.ht-hero`「旅行结束 / 一键清账」）、结算总金额（`.svm`） | 34px / 31px —— **冲击力是设计意图，不要压小** |
| 正文与标签（循真机阶梯） | 正文/列表 13–14px、分组标题 15px（`.st`）、导航标题 15.5px（`.an-t`）、卡片数值 19px（`.ov`）、金额输入 28px（`.ain`） | 见 `demo/index.html` 的「手机内排版比例」段 |
| 下限 | 功能性标签（表单标签 `.fl`、`BUDGET` `.bl`、`TOTAL/BILLS` `.ol`、成员/账单 `.rsl`） | **不小于 9.5px**，否则真机不可读 |

### 视觉约定：不设计头像

**本项目刻意不使用头像**（不用彩色首字母圆形占位），成员/付款人/收支一律用**姓名文字**表达：

| 场景 | 表现 |
|---|---|
| 手机顶部标签 | 用户名 + 身份（用颜色区分身份，不放圆形头像） |
| 房间成员 | 姓名胶囊 `.mname`，当前用户为黑底选中态并标注「· 我」 |
| 付款人选择 | 姓名胶囊（复用 `.pi` 选中样式），选中即黑底 |
| 结算收支明细 | 姓名 + 应收/应付 + 金额（不留头像位） |

`#uitest` 有守卫：一旦出现 `.ma` / `.mi` / `.bav` / `.pa` 等头像元素即 FAIL。

`#uitest` 内置**排版体检**：正文/标签超出阈值、或主视觉标题被压小（<30px）、或出现海报级字号（>36px）都会 FAIL。

### 无障碍（a11y）：对比度 / 语义 / 键盘

三件事都由 `#uitest` 真跑一遍验收，不是写在文档里的声明：

| 维度 | 现状 | 验收方式 |
|---|---|---|
| **对比度** | 设计令牌已按 WCAG 2.1 AA 校正：品牌橙**只当填充**（橙底配 `--on-pri` 深色字 6.25:1），白底上的橙字改用 `--pri-ink`（6.00:1）；次要灰 `--g400` 4.88:1；绿/红/琥珀语义色同样换成 AA 版本（点击文字都用 `var()` 令牌，不要写死 hex） | `#uitest` 遍历 6 个页面全部文本节点，按字号算 AA 阈值（<24px 要 4.5:1，大字 3:1），**逐个算对比度** |
| **语义** | 弹层 `role="dialog"` + `aria-modal` + `aria-labelledby`；toast / 演示字幕 / 同步徽标 `role="status" aria-live="polite"`；纯图标按钮补 `aria-label` | `#uitest` 校验属性齐全且 `aria-labelledby` 指向真实存在的标题节点 |
| **键盘** | `Esc` 逐层关闭（自检面板 → 导览 → 手机弹窗 → 退出演示模式）；弹层内 `Tab` 焦点循环；打开自动聚焦、关闭归还焦点；页面里 `<div onclick>` 卡片统一补 `tabindex="0" + role="button"` 并支持 Enter/空格激活 | `#uitest` 真实派发 `KeyboardEvent`（Esc 关闭、Tab 回环、Enter 进房间）验证端到端可用 |

> ⚠️ **刻意不用原生 `<dialog>`**：演示台是"3~4 台手机并排"的模拟机身，`.co` / `.mo` 是绝对定位在
> **手机壳内部**的弹层。原生 `<dialog>` 会进入 top layer 并相对视口居中 → 弹窗飞出手机屏、盖住整页，
> 直接破坏"每台手机 = 一个用户"的视觉隐喻。改用 `role`/`aria` + 焦点陷阱达到等价的键盘与读屏体验。
>
> `.pbt`（机身侧面按键）是纯装饰，已标 `aria-hidden="true"` —— 不要给它加语义。

## 八、测试策略

## 九、功能展示的完整性（"做了但演示里看不见"）

这是本项目最容易亏的地方：功能实现了，但**演示路径里没有它**，评委就永远看不到。三道机制把它钉死：

| 机制 | 位置 | 作用 |
|---|---|---|
| **功能清单 `FEATURES`** | `demo/index.html` | 40 项对外可见功能，每项一个 id |
| **导览 `covers: []` + `tourCoverage()`** | 同上 | 双向校验：清单有而导览没讲 = 漏；导览讲了而清单没有 = 脏。结果进 `#selftest` |
| **`data-feat="…"` 语义锚点**（69 个） | 各渲染函数 | 导览按**功能语义**高亮，不按样式类名 —— 排版重构不会让高亮失效 |

**步数要克制：同类功能必须合并。** 导览曾从 8 步一路加到 29 步（一个功能一步），
用户反馈"确实太长了"。**缩短不能靠删** —— 删掉就等于功能又看不见了。做法是**合并**：
把"币种 / 分类 / 分摊方式"并在一步、"改分摊 / 暂估改价 / 口头占位"并在一步、
"一键清账 / 各人收支 / 最简转账 / 结算前置校验 / 结清闭环"并在一步。
最终 **15 步覆盖全部 40 项功能**，单步最多讲 5 项。
`#selftest` 同时守住两端：**每个功能都要被讲到**（`tourCoverage()`），
**步数必须在 12~20 之间**（防它再长回去）。

演示路径本身也有守卫：

- `#uitest` 统计每台手机在自动演示里访问过的**页面种类**（<2 种即 FAIL），
  以及分镜字幕条数（≥20）、私账 / 截图识别 / 结清闭环是否真的演到。
- `#selftest` 与 `#tourtest` 都要求每台手机 **≥3 个导览环节**（15 步的分布是 4 / 3 / 3 / 3）。

### 踩过的坑（改导览前先看）

| 坑 | 症状 | 修法 |
|---|---|---|
| 只查"元素存在"不查可见 | `body.present` 把 `.tbar` 设为 `display:none`，前几步"高亮演示台"其实是**高亮到空气**，而 `#tourtest` 照样全绿 | `isShownDeep()` 沿祖先链查 `display/visibility`；导览期间给 body 加 `touring` 把工具条显示回来 |
| **先量位置后滚动** | 目标在手机内滚动区下方时（如结算页的"结算前置校验"），量到的是屏幕外坐标 → 高亮框停在屏幕外，观众什么都看不到 | 改成**先 `scrollIntoView` 再 `getBoundingClientRect`**，并用 instant 滚动避免量到动画中间态 |
| 控制条固定宽度挤字 | `.tour-ctrl .btn{flex:0 0 56px}` 把「退出」挤成竖排两个字 | 可收缩 `flex:1 1 0` + `min-width` + `white-space:nowrap` |
| **导览步骤改动了账目** | 为演示"已结清"的进度状态，某步的 `before()` 直接标了一笔已转账 —— 讲一遍就把人家的账标成"已转账"（实测污染了 `#uitest` 里的结算闭环用例） | **导览只读**：不调用 `toggleSettled`。进度条在 `0 / M` 状态下同样可见、同样被高亮，讲清楚即可；真要演示点击就现场点 |
| 步骤超时静默丢账 | `ocrStartScan` 内部 `setTimeout(2000)`，演示只等 1800ms 就 `ocrImport` → 票据整段白演，**只表现为"来源统计里少了 ocr"** | 等待时间必须 ≥ 被调函数的内部延时；`#uitest` 增加"演到截图识别/私账/结清闭环"的断言，缺了会红 |
